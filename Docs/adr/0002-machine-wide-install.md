# Architecture Decision Record: การติดตั้งแบบทั้งเครื่อง (Machine-wide / Admin install)

- **สถานะ:** Accepted (ข้อกำหนด R-022 ตกลง: 2026-10-20, ตัวเลือกออกแบบ 3 ข้อ: 2026-11-16, ลงมือและรีวิวรอบ 1: 2026-11-16) · **ยังไม่ได้ตรวจบนเครื่องจริง** (ดู Verification evidence)

## Context
ADR-0001 วางความเชื่อถือสามชั้นสำหรับส่วนเสริม แต่ชั้นที่ 3 ถูกเลื่อนไว้: ตัวติดตั้งเดิมเป็นแบบ per-user ลง `%LOCALAPPDATA%\Programs\SystemMonitor` ซึ่งผู้ใช้และโปรแกรมที่รันด้วยสิทธิ์ผู้ใช้เขียนทับได้ ดังนั้นมัลแวร์สิทธิ์ผู้ใช้เขียนทับ `SystemMonitor.exe` (รวมทั้งปลอมเป็น first-party) แล้วรอให้แอปถูกรันแบบผู้ดูแลระบบได้ ผู้ใช้ระบุใน R-022 ว่า "ถ้าขอสิทธิผู้ดูแลระบบตอนติดตั้งแล้ว ให้รันเป็นผู้ดูแลตลอดเลย" และเลือกให้ย้ายไป Program Files และใช้ Scheduled Task ระดับสูงสุด

ข้อกำหนดที่ต้องรักษา: ติดตั้งแบบ per-user เดิมต้องไม่เปลี่ยนและไม่ขอ UAC เอง, ไม่ติดตั้ง Windows service, config ของผู้ใช้ยังอยู่ที่ `%APPDATA%\SystemMonitor\config.wpf.json`, โหมด elevated ยังโหลดเฉพาะส่วนเสริม first-party ตาม ADR-0001

## Decision
1. **สองโหมดของตัวติดตั้ง** (`InstallScope`): `PerUser` (ค่าเดิมทุกอย่าง) และ `Admin` (เลือกด้วยช่องในหน้าต่างติดตั้งหรือ `/admin`) ตำแหน่งไฟล์ ชอร์ตคัต registry hive และวิธีเปิดพร้อม Windows ของแต่ละโหมดอยู่ใน `InstallLayout` ซึ่งเป็นข้อมูลล้วน ทดสอบได้โดยไม่แตะเครื่อง
2. **โหมด Admin:** `%ProgramFiles%\SystemMonitor` (เช่น `C:\Program Files\SystemMonitor`; เขียนได้เฉพาะผู้ดูแลระบบ; path มาจาก known folder ของ Windows), รายการ Apps & features ใน HKLM, ชอร์ตคัตของทั้งเครื่อง, ไฟล์ `install-mode.json` (`{"scope": "admin"}`) ที่ตัวติดตั้งเขียน และ Scheduled Task ชื่อ `SystemMonitor` แทน Run key `SettingsDir` (`%APPDATA%\SystemMonitor`) เหมือนเดิมทั้งสองโหมด
3. **ยกระดับด้วยการเปิดตัวเองซ้ำ ไม่ใช้ manifest** exe ตัวเดียวใช้ทั้งสองโหมด ถ้า manifest เป็น `requireAdministrator` การติดตั้ง per-user จะถูกบังคับขอ UAC ด้วย ตัวติดตั้งจึงขอสิทธิ์ครั้งเดียวด้วยการเปิดตัวเองซ้ำด้วย verb `runas` เมื่องานเป็นแบบ admin ตัวแอปทำเช่นเดียวกัน: ถ้ารันจาก `Program Files\SystemMonitor` เอง มี marker ที่ถูกต้อง และยังไม่ยกระดับ จะเปิดตัวเองซ้ำแบบยกระดับ **ก่อน** จับ lock single-instance (ไม่เช่นนั้นสำเนาที่ยกระดับจะเห็นว่ามีตัวเปิดอยู่แล้วแล้วออก) ถ้ามีสำเนาเปิดอยู่แล้วจะไม่ขอ UAC เปล่า ๆ (แต่รอสำเนาเก่าปิดได้สูงสุด 5 วินาทีก่อน เพราะ restart เปิดสำเนาใหม่ขณะสำเนาเก่ากำลังปิด) ถ้าผู้ใช้ปฏิเสธ UAC แอปทำงานต่อแบบไม่ยกระดับ (ไม่มี SMART) และปุ่ม restart ยังขอสิทธิ์ซ้ำได้ ตัวเปิดซ้ำใส่ `--elevation-attempted` (ตัวติดตั้งใส่ `--elevated`) เพื่อกันวนขอสิทธิ์ไม่รู้จบถ้าสำเนาที่เปิดกลับมายังไม่ยกระดับ และ `--no-elevate` ข้ามการเปิดซ้ำทั้งหมด (ใช้ตรวจ build) marker มีผลเฉพาะเมื่อแอปอยู่ใน Program Files จริง ไฟล์ที่ผู้ใช้ปกติวางเองที่อื่นไม่มีผล
4. **เปิดพร้อม Windows ด้วย Scheduled Task:** logon trigger เฉพาะผู้ใช้นั้น (ระบุด้วย SID), principal เป็นผู้ใช้นั้นด้วย `HighestAvailable` (ไม่ใช่ SYSTEM), ไม่ส่ง argument, ไม่จำกัดเวลา เรียก `schtasks.exe` ด้วย path เต็มและ argument list ไฟล์ XML ถูกวางในโฟลเดอร์ติดตั้ง (Program Files) ไม่ใช่ `%TEMP%` ช่องเปิดพร้อม Windows ในแถบข้างของแอปที่ติดตั้งแบบ admin เปิด/ปิด Task นี้ (ต้องยกระดับ ไม่เช่นนั้นช่องถูกปิดใช้งาน) แทนการเขียน Run key
5. **หลักที่ใช้: ไม่ลบ ไม่รัน ไม่จัดเตรียมไฟล์ ในที่ที่ผู้ใช้เขียนได้ ด้วยสิทธิ์ผู้ดูแลระบบ** (มีข้อยกเว้นที่ระบุในข้อจำกัด) เพราะการตรวจเป้าหมายก่อนลบ (`IsSafeTarget`) ไม่ atomic กับการลบ และไฟล์ใน `%TEMP%` สลับได้ก่อนที่โปรเซสสิทธิ์สูงจะอ่านหรือรัน ผลคือ
   - การลบรุ่น per-user ที่ถูกแทนที่ (`MigrateFromPerUser`) และการถอนรุ่นเก่า (Legacy ซึ่งรันคำสั่งถอนจาก registry ของผู้ใช้) ทำเฉพาะในสำเนาของตัวติดตั้งที่ **ไม่ยกระดับ** หลังสำเนาที่ยกระดับติดตั้งสำเร็จ (โหมด `/S` รอสำเนาที่ยกระดับและคืน exit code จริง) ถ้าตัวติดตั้งทั้งตัวรันยกระดับอยู่แล้ว จะแค่ปิดการเปิดพร้อม Windows ของรุ่น per-user และไม่ถอนรุ่นเก่า
   - ตัวถอนการติดตั้งแบบ admin ที่คัดลอกตัวเองไปรันต่อ ใช้โฟลเดอร์ `%ProgramData%\SysMonitor-uninstall-<guid>` ที่สร้างพร้อม ACL เฉพาะ Administrators/SYSTEM ในคำสั่งเดียว
   - การถอนแบบ admin **ไม่ลบไฟล์ในโฟลเดอร์ตั้งค่าของผู้ใช้** (`%APPDATA%\SystemMonitor`) แม้เลือกลบ: หน้าต่างบอกตำแหน่งให้ลบเอง (การถอนแบบ per-user ยังลบได้ตามเดิม)
   - Updater เมื่อแอปยกระดับ ดาวน์โหลดตัวติดตั้งลง `%ProgramData%\SysMonitor-update-<guid>` ด้วย ACL เดียวกัน ก่อนสร้างใหม่จะพยายามลบโฟลเดอร์ `SysMonitor-update-*` เก่าทั้งหมดใน ProgramData แต่เฉพาะที่ไม่ใช่ลิงก์และ **เจ้าของเป็น Administrators/SYSTEM** (ผู้ใช้ปกติสร้างโฟลเดอร์ชื่อซ้ำใน ProgramData ได้ จึงใช้ชื่ออย่างเดียวไม่ได้) แอปที่ไม่ยกระดับใช้ `%TEMP%` เหมือนเดิม
   - ตัวติดตั้งทุกสำเนาถือไฟล์ของตัวเองไว้แบบไม่แชร์การเขียน/ลบ/เปลี่ยนชื่อ (`SelfImage`) ตั้งแต่เริ่มทำงาน เพราะไฟล์ที่กำลังรันเปลี่ยนชื่อได้ และสำเนาที่ยกระดับคัดลอกตัวเองจาก path เดิมไปเป็นตัวถอนใน Program Files; การถือไว้กันการสลับไฟล์ระหว่าง UAC และหลังสำเนาที่ยกระดับเริ่ม ถ้าล็อกไฟล์ไม่ได้ (เช่น มีโปรเซสอื่นเปิดไฟล์ไว้โดยอนุญาตให้ลบ/เปลี่ยนชื่อ) ตัวติดตั้งจะไม่ติดตั้งแบบทั้งเครื่องและไม่ขอ UAC (`SelfImage.Require`)
6. **ลำดับของการติดตั้งแบบ admin:** ต้องมีสิทธิ์ผู้ดูแลก่อนเขียนอะไร (ไม่มีสิทธิ์ = ปฏิเสธ ไม่แตะอะไร) → ไฟล์/ส่วนเสริม/ตัวถอน/marker/ชอร์ตคัต → รายการ Apps & features → Scheduled Task ความล้มเหลวของ Task หรือไฟล์ส่วนเสริมที่เขียนไม่ได้ถูกรายงานท้ายสุดโดยที่ตัวติดตั้งยังถอนได้
7. **ส่วนเสริมของบุคคลที่สาม:** ผู้ดูแลระบบคัดลอกเข้า `Program Files\SystemMonitor\extensions\<id>\` เอง แล้วใช้กลไกอนุมัติเดิมของ ADR-0001 ไม่มีช่องทางใหม่ และโหมด elevated ยังโหลดเฉพาะ first-party
8. **บัญชีที่รองรับ:** ผู้ใช้ที่เป็น Administrator เองและยืนยัน UAC ด้วยบัญชีเดียวกัน (config จึงอยู่ใน `%APPDATA%` ของคนเดียวกัน)

## Alternatives
- **manifest `requireAdministrator`:** ถูกปฏิเสธ — บังคับ UAC กับการติดตั้ง per-user ซึ่งขัดข้อกำหนด
- **exe ตัวที่สองที่มี manifest บังคับ admin:** ถูกปฏิเสธ — ขนาดตัวติดตั้งเพิ่มเท่าตัวโดยได้ผลเท่ากับการเปิดตัวเองซ้ำ
- **Windows service:** นอกขอบเขตตามที่ผู้ใช้ระบุ (ใช้ Scheduled Task)
- **Run key ใน HKLM:** ถูกปฏิเสธ — เปิดแอปแบบไม่ยกระดับ ต้องขอ UAC ทุก logon
- **ลบรุ่น per-user ด้วยสิทธิ์ผู้ดูแลโดยเปิดไฟล์ด้วย handle ตรวจทีละชั้น:** ถูกเลื่อนไว้ — ซับซ้อนเกินกว่าวิธีให้สำเนาที่ไม่ยกระดับลบเอง

## Consequences

### ข้อดี (Positive)
- ปิดช่องโหว่ที่ ADR-0001 ยอมรับไว้ (exe เขียนทับได้) สำหรับผู้ที่เลือกติดตั้งแบบ admin: exe, ส่วนเสริม first-party และตัวถอนอยู่ในที่ที่ผู้ใช้ปกติแก้ไม่ได้
- ผู้ใช้ได้แอปรันแบบผู้ดูแลระบบตามปกติโดยไม่ต้องกดปุ่ม และไม่มี UAC ตอนเปิดเครื่อง (ยกเว้นเมื่อใช้ `--no-elevate` หรือปฏิเสธ UAC ตอนเปิดเอง)
- โหมด per-user ไม่เปลี่ยน

### ข้อเสีย / ข้อจำกัดที่ยอมรับแล้ว (Negative / Accepted Limitations)
1. การยกระดับด้วยบัญชีแอดมินอื่น (ผู้ใช้ปกติใส่รหัสผ่านของ admin คนอื่นที่ UAC) ไม่รองรับ: `%APPDATA%` และตำแหน่งของ per-user จะเป็นของบัญชีนั้น
2. ผู้ใช้ปฏิเสธ UAC: แอปรันแบบไม่ยกระดับ SMART ใช้ไม่ได้จนกว่าจะกดรันใหม่แบบ admin ไม่ถือเป็นข้อผิดพลาด
3. ตัวติดตั้งที่ถูกรันยกระดับทั้งตัวตั้งแต่แรก (เช่นจาก shell ที่เป็น admin) ไม่ลบไฟล์ของรุ่น per-user และไม่ถอนรุ่นเก่า (Legacy) ให้ — ถอนเองได้จาก Apps & features ผลคือมีสองรุ่นอยู่พร้อมกันได้ รุ่น admin ชนะการตรวจ (`DetectInstalledScope`) และการเปิดพร้อม Windows ของรุ่น per-user ถูกปิด
4. Updater ไม่ตรวจลายเซ็นหรือแฮชของตัวติดตั้งที่ดาวน์โหลด (เป็นเช่นนั้นอยู่เดิม) การวางในโฟลเดอร์เฉพาะผู้ดูแลระบบปิดเฉพาะช่องว่างการสลับไฟล์ ไม่ได้พิสูจน์ที่มาของไฟล์
5. `%ProgramData%\SysMonitor-update-*` ค้างอยู่จนกว่าจะอัปเดตแบบยกระดับครั้งถัดไป (ลบเองตอนนั้น) ส่วน `SysMonitor-uninstall-*` ถูกส่งให้ Windows ลบตอนรีสตาร์ท ซึ่งอาจล้มเหลวได้เงียบ ๆ
6. การตรวจ `IsSafeTarget` ของรุ่น per-user ยังเป็น check-then-delete ตามที่ระบุไว้ในโค้ดเดิม ที่ยอมรับได้เพราะไม่ทำด้วยสิทธิ์ผู้ดูแลระบบ
7. Windows ยอมรับ XML ของ Task และ Task ที่ระบุผู้ใช้ด้วย SID ทำงานจริงหรือไม่ **ยังไม่ได้พิสูจน์** (test ตรวจเฉพาะโครงสร้าง XML และ argument ของ `schtasks`)
8. ไม่มีเครื่องมือช่วยติดตั้งส่วนเสริมของบุคคลที่สามเข้า Program Files นอกจากการคัดลอกด้วยมือ
9. การเปลี่ยนโหมดระหว่าง per-user ↔ admin ทำได้ทางเดียวผ่านตัวติดตั้ง (per-user → admin); ย้อนกลับ ต้องถอนแล้วติดตั้งใหม่
10. ตัวติดตั้งที่ถูกรันยกระดับทั้งตัวตั้งแต่แรก (เช่นจาก shell ที่เป็น admin) มีช่วงสั้น ๆ ระหว่างเริ่มโปรเซสกับการถือไฟล์ตัวเอง (`SelfImage.HoldOwn`) ที่ไฟล์ถูกสลับได้ — ปิดสมบูรณ์เฉพาะทางที่สำเนาไม่ยกระดับเป็นผู้เปิดซ้ำ (ซึ่งถือไฟล์ไว้ตลอด UAC) แต่ถ้าถือไฟล์ไม่ได้เลย การติดตั้งแบบทั้งเครื่องถูกปฏิเสธ
11. แอปที่ยกระดับตลอด เขียน `config.wpf.json(.tmp)` และ log ใน `%APPDATA%\SystemMonitor` ซึ่งผู้ใช้เขียนได้ด้วย path (พฤติกรรมเดิมของแอป ไม่ได้เปลี่ยนใน R-022 แต่ตอนนี้เกิดทุกครั้ง) จึงเป็นช่องที่ลิงก์ในโฟลเดอร์นั้นอาจพาให้ไฟล์ปลายทางถูกเขียนด้วยสิทธิ์สูง; ยังไม่ได้แก้
12. Task ของแอปที่ยกระดับรับ environment ของผู้ใช้ (รวม `HKCU\Environment`) โปรเซสสิทธิ์ผู้ใช้จึงอาจตั้ง `DOTNET_*`/`CORECLR_PROFILER*` ให้โค้ดรันด้วยสิทธิ์สูงตอน logon ได้ (ตัวติดตั้งที่ยกระดับก็เช่นกัน ถ้า UAC ส่ง environment นั้นต่อ) — ปิดเฉพาะ startup hook ด้วย `StartupHookSupport=false` ในโปรเจกต์ WPF และ Setup ส่วนที่เหลือปิดไม่ได้จากโค้ด managed และ **ยังไม่ได้ทดสอบบนเครื่องจริง** ข้อดีข้อแรกด้านล่างจึงมีเงื่อนไขนี้
13. เจ้าของโฟลเดอร์ admin-only ที่สร้างขึ้น (`SysMonitor-update-*`, `SysMonitor-uninstall-*`) ไม่ได้ตั้งค่าเอง พึ่ง default owner ของ token ที่ยกระดับ (Administrators) การตรวจเจ้าของตอนลบจึงล้มแบบปลอดภัย (ไม่ลบ) ถ้าเจ้าของเป็นอย่างอื่น
14. การถอน: ถ้าลบ Scheduled Task ไม่สำเร็จ การถอนทำต่อและอาจเหลือ Task ที่ชี้ไป exe ที่ถูกลบแล้ว (ไม่แจ้งเป็นข้อผิดพลาด)
15. ติดตั้งแบบทั้งเครื่องโดยไม่ติ๊ก "เปิดพร้อม Windows" จะได้ Task ที่ **ปิดอยู่** (`Enabled=false`) ไม่ใช่ไม่มี Task: ช่องเปิดพร้อม Windows ในแอปเปิด/ปิด Task ได้ (ต้องยกระดับ) และตอนอัปเดตตัวติดตั้งอ่านสถานะจริงแล้วสร้างใหม่ด้วยสถานะเดิม (ไม่เปิดกลับ ไม่ลบ) ติดตั้งจากรุ่นก่อนการแก้นี้ที่ไม่มี Task ช่องในแอปจะเป็นสีเทาจนกว่าจะติดตั้งใหม่ (แอปไม่สร้าง Task เอง)
16. ตัวติดตั้งที่เปิดแบบ `--admin` (ไม่ใช่ `/S`) รอสำเนาที่ยกระดับแล้วย้ายรุ่น per-user ให้ เฉพาะเมื่อสำเนานั้นจบด้วย exit code 0 ซึ่งหมายถึงติดตั้งสำเร็จจริง (ปิดหน้าต่างโดยไม่ติดตั้งคืน 2) และมีรุ่น admin อยู่จริง แต่ไม่ถอนรุ่นเก่า (Legacy) ในทางนี้ — รุ่นเก่าถอนได้ในวิซาร์ดที่ไม่ยกระดับ
17. การถอนแบบ admin: ตัวถอนที่ไม่ยกระดับ (`uninstall.exe` ใน Program Files) เปิดสำเนาที่ยกระดับแล้ว **ไม่รอ** (เพราะตัวมันเองคือไฟล์ที่ตัวจบงานต้องลบ) exit code ของ `/S` ในการถอน (ทั้ง per-user และ admin) บอกเพียงว่าตัวจบงานเริ่มแล้ว ไม่ได้บอกว่าลบสำเร็จ — ถ้าตัวจบงานล้มเหลวผู้เรียกไม่รู้
