# Architecture Decision Record: สถาปัตยกรรมส่วนเสริม (Extension Architecture)

- **สถานะ:** Accepted (ตัดสินใจ: 2026-10-13, ชั้นความปลอดภัย: 2026-10-14, บันทึก: 2026-11-16)

## Context
SystemMonitor ถูกออกแบบใหม่ตามคำขอของผู้ใช้ (ตาม Requirement R-021) ให้แยกสถาปัตยกรรมออกเป็นโฮสต์หลัก (Core Host) และส่วนเสริม (Extensions) เพื่อให้สามารถขยายความสามารถ เช่น การอ่านค่าอุณหภูมิฮาร์ดดิสก์ผ่าน SMART โดยไม่ต้องแก้ไขโค้ดหลักของแอปพลิเคชัน

ความท้าทายสำคัญและสิ่งที่ต้องรักษาไว้:
- พฤติกรรมเดิมของแอปพลิเคชันต้องคงเดิม ไม่กระทบการทำงานหลัก
- ความกังวลด้านความปลอดภัย: หากโฮสต์ทำงานด้วยสิทธิ์ระดับสูง (Elevated / Admin) โฮสต์จะต้องไม่รันโค้ดส่วนเสริมที่มีสิทธิ์สูงเกินควรโดยไม่ผ่านการตรวจสอบความปลอดภัยที่รัดกุม

## Decision
การตัดสินใจทางสถาปัตยกรรมตามที่ผู้ใช้กำหนดมีดังนี้:
1. **รูปแบบส่วนเสริม:** ใช้ managed .NET DLL extensions ที่โหลดผ่าน collectible `AssemblyLoadContext`
2. **ขอบเขตเฟสแรก:** เริ่มต้นด้วย Core + SMART เป็นส่วนเสริมแบบ first-party ตัวแรก
3. **แหล่งที่มาและความปลอดภัย:** โหลดส่วนเสริมเฉพาะจากโฟลเดอร์ติดตั้ง พร้อมตรวจสอบความถูกต้องด้วย SHA-256
4. **ชั้นความปลอดภัย (Trust Layers 1 & 2):** 
   - **Layer 1 (First-party):** แฮช SHA-256 ของ manifest ฝังมาใน exe หลัก (resource `first-party-extensions.json`, ตรวจสอบผ่าน `FirstPartyAllowlist.FromAssembly`)
   - **Layer 2 (User-approved):** สำหรับโฮสต์ปกติ โหลด first-party หรือส่วนเสริมที่ผู้ใช้อนุมัติไว้แล้วใน `%ProgramData%\SystemMonitor\approved-extensions.json` (จัดเก็บผ่าน `ApprovalStore` ซึ่งกำหนด ACL ให้เขียนได้เฉพาะ Administrators/SYSTEM เท่านั้น และป้องกัน reparse point รวมถึง lock file)
   - โฮสต์ที่รันด้วยสิทธิ์สูง (Elevated) จะอนุญาตให้โหลดเฉพาะส่วนเสริมที่เป็น first-party เท่านั้น (หากไม่ใช่จะคืนสถานะ `NotTrustedWhenElevated`)
5. **ฝั่ง DiskInfo:** เป็นผู้ให้ `DiskInfoCore.dll` (native) ที่ส่วนเสริม SMART เรียกเอง; DiskInfo ไม่เปลี่ยนโครงสร้างในรอบนี้
6. **Layer 3 (Program Files):** การย้ายไปติดตั้งที่ Program Files ไม่ได้รวมอยู่ในการตัดสินใจรอบนี้ แต่ถูกแยกไปเป็นข้อกำหนดต่างหากใน R-022 (ตัดสินใจและลงมือใน `Docs/adr/0002-machine-wide-install.md`)

## Alternatives
- ไม่ได้บันทึกรายละเอียดทางเลือกอื่นไว้ นอกจากที่ผู้ใช้เลือก

## Consequences

### ข้อดี (Positive)
- แยกส่วนประกอบการทำงานออกเป็นอิสระ ช่วยให้การพัฒนาและเพิ่มฟีเจอร์ใหม่ (เช่น SMART) ทำได้ง่ายขึ้นโดยไม่กระทบโค้ดหลัก
- ควบคุมความปลอดภัยได้อย่างเข้มงวดผ่านการตรวจสอบแฮช SHA-256 และจำกัดสิทธิ์การโหลดเมื่อโฮสต์รันด้วยสิทธิ์ผู้ดูแลระบบ

### ข้อเสีย / ข้อจำกัดที่ยอมรับแล้ว (Negative / Accepted Limitations)
1. ตัวช่วยอนุมัติเขียน Diag log แม้จะปิดการใช้งาน diagnostics ไว้
2. เมื่อส่วนเสริมถูกปิด/โหลดใหม่/โฮสต์ปิด โฮสต์รอการเรียกที่ค้างอยู่ (เช่น `GetView`) ไม่เกิน 5 วินาที หากยังไม่จบจะ dispose ต่ออยู่ดีพร้อมเขียน log (`ExtensionSlot.RetireAndDispose`) — ส่วนเสริมที่ช้าจึงอาจถูก dispose ขณะยังมีการเรียกค้าง
3. **ช่องโหว่การติดตั้งแบบ per-user:** เนื่องจาก exe หลักอยู่ในโฟลเดอร์ที่ผู้ใช้เขียนได้ มัลแวร์ที่รันด้วยสิทธิ์ผู้ใช้สามารถเขียนทับ exe ได้ ช่องโหว่นี้ปิดได้เฉพาะผ่านการติดตั้งแบบ admin ซึ่งทำเป็นทางเลือกใน R-022 (ดู ADR-0002; ยังไม่ได้ตรวจบนเครื่องจริง) ผู้ที่ติดตั้งแบบ per-user ยังมีช่องโหว่นี้
4. ปุ่ม "รันใหม่แบบผู้ดูแลระบบ" จะแสดงขึ้นเมื่อส่วนเสริม SMART โหลดอยู่ แม้ว่าจะไม่มีไฟล์ `DiskInfoCore.dll` ก็ตาม
5. เมธอด `ExtensionHost.Reload` จะทำการล้าง cached display name
6. การทดสอบ `ExtensionHost_SetEnabled_LeavesRealConfigUntouched` จะทำการอ่านไฟล์ `%APPDATA%` จริง (อ่านอย่างเดียว)
7. การ build โดยตรงผ่าน IDE หรือคำสั่ง `dotnet build` โดยไม่ผ่านสคริปต์ `build-wpf.cmd` อาจทำให้ฝัง `first-party-extensions.json` เวอร์ชันเก่า
8. การรัน PackTool สองตัวพร้อมกันด้วย allowlist เดียวกันอาจทำให้สูญเสียแฮชหนึ่งรายการ (ต้องรันผ่านสคริปต์แบบเรียงลำดับ)
9. ไฟล์ในแพ็กเกจอาจถูกล็อกระหว่างการอัปเกรด ส่งผลให้ส่วนเสริมแสดงสถานะ `HashMismatch` หรือ `UnsafePath` จนกว่าจะรันตัวติดตั้งใหม่อีกครั้ง
10. การทดสอบ 2 ตัวถูกข้าม (เนื่องจากไม่สามารถสร้าง file symlink บนเครื่องพัฒนาได้) จึงยังไม่สามารถพิสูจน์การป้องกัน file link ด้วยสถานการณ์จริงได้
11. ไม่มีระบบตลาด, การดาวน์โหลด หรือการอัปเดตส่วนเสริมอัตโนมัติ ไม่มีแพ็กเกจจากบุคคลที่สาม และไม่มีระบบตรวจจับมัลแวร์ในตัว (ถือเป็นหน้าที่ของ Antivirus)

## Verification evidence
- **ผลการทดสอบ:** บันทึกล่าสุดใน `Requirements.md` R-021 เฟส 4 คือ MSTest 609 ผ่าน ข้าม 2 (`SysMonitor.Tests`) และรันซ้ำได้ผลเดิมเมื่อ 2026-11-16 (609 ผ่าน, 2 ข้าม, 0 ล้ม)
- **การทดสอบคุณสมบัติด้านความปลอดภัย:** ตรวจสอบด้วย `ExtensionLoaderTests` (hash, ความเชื่อถือ first-party/elevated, reparse point, AssemblyLoadContext), `ExtensionHostTests`, `ApprovalStoreTests`, `AclPolicyTests`, `ExtensionApprovalTests`, `PackToolTests`, `SampleExtensionTests` ใน `SysMonitor.Tests/Extensions` และ `InstallerExtensionTests` ใน `SysMonitor.Tests`
- **สิ่งที่ยังไม่ได้ตรวจสอบบนเครื่องจริง:** 
  - ขั้นตอนการอนุมัติผ่านหน้าจอ UAC จริง
  - ACL ของโฟลเดอร์ `%ProgramData%` บนระบบจริง
  - การป้องกัน symlink บนเครื่องจริง
  - การเทียบหน้าจอจริงก่อนและหลัง

## Follow-ups
- ตรวจรับ **R-022** (การติดตั้งแบบ Admin / Program Files / Scheduled Task) บนเครื่องจริง — ลงมือแล้วตาม ADR-0002
- การเทียบค่าอุณหภูมิ ±2 °C (เกี่ยวข้องกับข้อกำหนด R-019/R-020)
- การตรวจสอบยืนยันผลบนเครื่องจริง (Real-machine verification)
