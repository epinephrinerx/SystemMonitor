# แผนงาน R-002 / R-003 / R-004 / R-006 จาก Coding Owner (planner, อ่านอย่างเดียว)

**ภาพรวม:** ทำได้ทั้ง 4 ข้อ ไม่ต้องเพิ่ม dependency และแก้แค่ไฟล์ใน scope ของ handoff มีข้อยกเว้นหนึ่งจุด (D5) ผมแนะนำแบ่งเป็น 5 เฟส เรียงจากเสี่ยงน้อยไปเสี่ยงมาก และมี 6 เรื่องที่ต้องให้ Writing Owner หรือผู้ใช้ตัดสินก่อนเริ่มเฟสที่เกี่ยวข้อง (หัวข้อ 4)

ผมยังไม่ได้รัน `dotnet test` หรือ build เพราะบทบาทนี้อ่านอย่างเดียว และ build จะเขียนไฟล์ลง `bin/` กับ `obj/` ตัวเลข 198/198 ที่อ้างถึงจึงมาจาก handoff ไม่ได้มาจากการรันของผม และผมไม่ได้แตะไฟล์ untracked ใน `Docs/`

## 1. ความเป็นไปได้รายข้อ

### R-002 · ปุ่มนำทางหน้า Full และ Overall — ทำได้ เสี่ยงต่ำ

**สิ่งที่ยืนยันจากโค้ด**
- ปุ่มที่มีอยู่ตอนนี้
  - หน้า Overall มี `FullScreenButton` (E740), `CollapseButton` (E921) และ `CloseButton` (`MainWindow.xaml:349-361`)
  - หน้า Full มี `FullCollapseButton` (E73F) และ `FullCloseButton` (`MainWindow.xaml:438-447`)
- การผูกปุ่มอยู่ที่ `MainWindow.xaml.cs:94-101`
  - `CollapseButton` ไป Widget อยู่แล้ว เปลี่ยนแค่ icon กับ tooltip ก็ได้ปุ่ม "เปิดเป็น Widget"
  - `FullCollapseButton` ไป Overall อยู่แล้ว เปลี่ยนเป็นปุ่ม "ไปหน้ารวม"
  - งานใหม่จริงมีปุ่มเดียว คือปุ่ม Full → Widget
- การสลับ Full → Widget ตรง ๆ มีอยู่แล้วผ่าน double-click (`MainWindow.xaml.cs:515-516`) และ `SetMode` ก็คืนตำแหน่งจาก `_beforeFull` ให้ (`:334-338`) พฤติกรรม "ขนาดและตำแหน่งตาม view ปลายทาง" จึงใช้ของเดิมได้เลย
- ปุ่มปิดทุกหน้าเรียก `Close()` แล้วไหลเข้า `OnClosing` ซึ่งตรวจ `CloseAction` (`:1277-1285`) โค้ดส่วนนี้ไม่ต้องแก้
- ข้อกังวลใน handoff เรื่องต้องปรับ `RestartAndViewTests` หรือ `WindowGeometryTests` นั้น**ไม่ต้องปรับ** ผม grep แล้วไม่มี test ไหนอ้างถึงชื่อปุ่มหรือ `MainWindow`

**จุดเสี่ยง**
- ตอนนี้ยังไม่มีปุ่มไหนมี ToolTip เลย ต้องสร้างกลไกใหม่
- การเปลี่ยนภาษาเกิดในหน้า Overall (`:923-934`) ซึ่งเรียกแค่ `BuildSidebar` กับ `BuildContextMenu` ถ้าตั้ง tooltip ครั้งเดียวใน constructor จะเหลือภาษาเก่าค้างอยู่ ต้องมีจุดรีเฟรชที่ถูกเรียกตอนเปลี่ยนภาษาด้วย
- ห้ามลบคีย์ `collapse`, `expand_hint`, `fullscreen` และ `exit_fullscreen` เพราะ context menu ยังใช้อยู่ (`:751-752`)
- ขอบบนของทั้งสองหน้าอยู่ใน `CornerBand` ของ hit-test แต่ `OverControl` กันไว้ให้ ButtonBase แล้ว (`:480`, `:617-629`) ปุ่มใหม่ต้องเป็น `Button` จึงจะรับคลิกได้

### R-004 · ปุ่มเลื่อนซ้าย/ขวาเห็นชัดตลอด — ทำได้ เสี่ยงต่ำ แต่มีผลกับ layout

**สิ่งที่ยืนยันจากโค้ด**
- ปุ่ม `WidgetPrevButton`/`WidgetNextButton` ใช้ style `HoverIconButton` ที่มี Opacity 0.35 และชัดเต็มที่เฉพาะตอนเมาส์อยู่บนหน้าต่าง (`App.xaml:75-85`) สีตัวอักษรคือ `#94a3b8` แบบตายตัว (`App.xaml:47`) ซึ่งตัดกับพื้นได้ไม่ดีใน light theme (ค่าเริ่มต้นคือ `light`, `AppConfig.cs:20`)
- เรื่อง "ลอยพ้นขอบ" ตำแหน่งจริงจากโค้ดไม่ได้อยู่นอก panel
  - Panel มี margin 12 และขอบ 1, WidgetView มี margin 12, ปุ่มมี margin -10 (`MainWindow.xaml:242-273`)
  - ปุ่มจึงอยู่ที่ x ≈ 15–33 ขณะที่ panel เริ่มที่ 12 คือยังอยู่ในขอบ panel ประมาณ 3px แต่เกินพื้นที่เนื้อหาออกไป
  - ปัญหาหลักที่ผู้ใช้เห็นจึงน่าจะเป็นความจางกับสีเทา มากกว่าตำแหน่ง ต้องแก้ทั้งสองเรื่องให้ผ่านเกณฑ์ตรวจรับ

**จุดเสี่ยง**
- `HoverIconButton` ถูกใช้กับ `WidgetCloseButton` ด้วย (`MainWindow.xaml:257`) ถ้าแก้ style นี้ทั้งก้อน ปุ่มปิดจะเปลี่ยนไปด้วย ซึ่งนอก scope ควรทำ style ใหม่แยกต่างหาก
- ถ้าย้ายปุ่มเข้ามาในพื้นที่เนื้อหา ปุ่มจะทับแถบ bar ที่แผ่เต็มความกว้าง (`MainWindow.xaml:303-310`) ต้องเว้นช่องซ้ายขวา
  - แต่ที่ขนาดเล็กสุด 200 px (`AppConfig.cs:115`) ในหน้า per-core ที่แบ่ง 2 คอลัมน์ (`WidgetViewModel.cs:329`) เนื้อหาเหลือไม่ถึง ~70px ต่อคอลัมน์ แถบจะเกือบหายไป
  - ทางที่ผมแนะนำ: ให้ปุ่มอยู่ในพื้นที่ padding ของ panel ต่อไป เลื่อนให้อยู่ในขอบชัดเจน ≥ 4px เพิ่มพื้นหลังทึบบาง ๆ (chip) และเว้นช่องให้เนื้อหาน้อยที่สุด

### R-006 · ปุ่มหยุด/เล่นการวนหน้า — ทำได้ เสี่ยงต่ำถึงกลาง

**สิ่งที่ยืนยันจากโค้ด**
- เงื่อนไขการวนอยู่จุดเดียวที่ `MainWindow.xaml.cs:264-265` ส่วนการเลื่อนหน้าอยู่ที่ `:294-298` เพิ่มเงื่อนไข "ไม่ได้หยุด" ตรงนั้นพอ
- ค่ายังอัปเดตขณะหยุด เพราะเมื่อมี snapshot ใหม่ (`fresh`) โค้ดก็ยังไปเรียก `UpdateWidget` (`:299`) โดยไม่ขึ้นกับการวน ข้อนี้พิสูจน์จากโค้ดได้เลย
- ปุ่มเลื่อนขณะหยุดใช้ได้โดยไม่ทำให้กลับมาวนเอง เพราะ `Step()` (`:313-322`) เปลี่ยนหน้าและรีเซ็ต `_lastRotate` โดยไม่แตะสถานะหยุด
- สถานะหยุดเป็นแค่ field ใน memory ไม่เขียนลง config ตรงตามข้อ "ไม่รวม"

**จุดเสี่ยง**
1. **กดเล่นต่อแล้วกระโดดหน้าทันที:** ถ้าหยุดไว้นานกว่า 5 วินาที `_lastRotate` จะเก่า พอกดเล่นต่อ tick ถัดไป (ภายใน 400ms) จะสลับหน้าทันที ขัดกับ "วนต่อจากหน้าปัจจุบันทุก 5 วินาที" ต้องรีเซ็ต `_lastRotate` ตอนกดเล่นต่อ
2. **ชนกันที่มุมบนขวา:** ปุ่มปิดอยู่มุมบนขวา (margin -4) ส่วนแถวหัวข้อของเนื้อหามี `WidgetValue` ชิดขวาและ `WidgetTitle` เว้นขวา 96 (`MainWindow.xaml:291-301`) ปุ่มที่สองจะเข้าใกล้ตัวเลขค่าหลัก ยิ่งถ้าความสูงน้อย (ขั้นต่ำ 64) หรือ FontScale 1.6
3. **badge `⏸ ค้าง` มุมบนซ้ายอาจทับ `WidgetTitle`** ด้วยเหตุผลเดียวกัน badge ควรตั้ง `IsHitTestVisible=False` เพราะอยู่ในเขต corner-resize
4. **การสลับโหมดระหว่าง session:** `SetMode(Widget)` เรียก `RebuildViews` แต่ไม่รีเซ็ต `ViewIndex` (`:372-375`, `WidgetViewModel.cs:277`) ต้องตัดสินว่าสถานะหยุดคงอยู่หลังไป Overall/Full แล้วกลับมาหรือไม่ (ดู D2)
5. **ทดสอบยาก:** `MainWindow` สร้างใน unit test ไม่ได้ (ต้องมี Sampler และ tray) ต้องแยกตรรกะ "ควรวนหรือไม่" ออกมาเป็นฟังก์ชัน pure ถึงจะเขียน test ได้ (ดู D5)

### R-003 · Resize widget แบบคงสัดส่วน และสเกลเนื้อหาตามขนาด — ทำได้ เสี่ยงสูงที่สุด

**สิ่งที่ยืนยันจากโค้ด**
- คณิตของ resize แยกเป็น pure อยู่แล้วใน `WindowGeometry.Resize` (`WindowGeometry.cs:90-126`) และมี test คลุมแน่น (`WindowGeometryTests.cs`) เพิ่มฟังก์ชันแบบคงสัดส่วนข้าง ๆ แล้วให้ `MainWindow.Resize` (`:656-683`) เรียกเฉพาะโหมด Widget ได้ Overall และ Full จะไม่เปลี่ยน ตรงกับข้อ "ไม่รวม"
- ขอบเขตขนาด widget คือ min 200×64 และ max 900×400 (`AppConfig.cs:115-116`) ที่สัดส่วนเริ่มต้น 270:104 ≈ 2.6 ทั้ง min และ max ทำได้โดยไม่ขัดกัน
- FontScale ปรับ font ramp ระดับ Application (`MainWindow.xaml.cs:1125-1137`) ซึ่งกระทบทุก view ถ้าเอา ramp มาใช้สเกล widget ด้วย Overall/Full จะเปลี่ยนตาม จึงควรสเกลเฉพาะชั้นเนื้อหาของ WidgetView ด้วย LayoutTransform แล้วคูณซ้อนกับ FontScale
  - สูตรที่เสนอ: ขนาดตัวอักษร = base × FontScale × widgetScale
  - widgetScale = min(panelW/refW, panelH/refH) แล้ว clamp

**จุดเสี่ยง (มากที่สุดในงานชุดนี้)**
1. **สัดส่วนต้องคิดจากขนาด panel ไม่ใช่ขนาดหน้าต่าง** `_resizeOrigin` รวม ShadowPad ด้านละ 12 ไว้ด้วย (`:502`, `WindowGeometry.cs:23`) ถ้าคิดจากหน้าต่าง สัดส่วนจะเพี้ยนตามขนาด
2. **Clamp ต้องคงสัดส่วน** ต้องหาค่า scale ที่ทั้งกว้างและสูงอยู่ในช่วง min–max พร้อมกัน ถ้าค่าใน config อยู่นอกช่วง (แก้มือ หรือ `ApplyPanelSize` ไม่ clamp, `:189-190`) ช่วงที่เป็นไปได้อาจว่าง ต้องมี fallback
3. **ขยายหลุดจอ:** ตำแหน่งแรกของ widget คือมุมล่างขวาของ work area (`:219-221`) ถ้าลากขอบซ้าย/ขวาแล้วยึดขอบบนไว้ ความสูงจะงอกลงไปใต้ taskbar ทันที ระหว่างลากไม่มีการเรียก `KeepOnScreen` (ดู D4)
4. **Viewbox แบบ Uniform ใช้ไม่ได้ตรง ๆ** ความสูงเนื้อหาแต่ละหน้าไม่เท่ากัน (CPU 4 แถว, RAM 1 แถว) ตัวอักษรจะเต้นขึ้นลงทุกครั้งที่วน ต้องคิด scale จากขนาด panel เท่านั้น ไม่ใช่จากขนาดเนื้อหา
5. **ค่า reference กับผู้ใช้เดิม:** ผู้ใช้ที่เคยขยาย widget ไว้จะเห็นตัวอักษรใหญ่ขึ้นทันทีหลังอัปเกรด โดยขนาดใน config ไม่เปลี่ยน (ดู D3)
6. **ค่า reset ไม่ตรงกับ default:** `ResetSize` ตั้ง `WidgetH = 90` (`:447`) ขณะที่ default คือ 104 (`AppConfig.cs:90`) และ XAML ใช้ 114 = 90+24 (`MainWindow.xaml:14`) เมื่อสัดส่วนถูกล็อก กด reset จะได้สัดส่วน 3.0 แทน 2.6 และตัวอักษรเล็กลง
7. **ภาระ render:** หน้าต่างแบบ per-pixel alpha วาดด้วย software (`:259-262`) การ layout ใหม่ทุก mouse-move ระหว่างลากจะหนักขึ้น ต้องลองลากจริงดูว่ากระตุกหรือไม่

### เฟส 4a — R-003 ส่วนที่ 1: resize แบบคงสัดส่วน
- **ไฟล์ที่แก้**

### เฟส 4b — R-003 ส่วนที่ 2: สเกลเนื้อหาตามขนาด
- **ไฟล์ที่แก้**

- **เกณฑ์จบ:** test ผ่านทั้งหมด ตัวอักษร ค่า และแถบใน widget ขยาย-หดตามขนาดจริงที่เห็น ตัวอักษรไม่เต้นเมื่อสลับหน้า CPU↔RAM ที่ขนาดคงที่ Overall/Full ไม่เปลี่ยน slider FontScale ยังมีผลกับ widget และลากแล้วไม่กระตุกจนใช้งานไม่ได้
